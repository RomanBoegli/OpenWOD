OpenWOD now comes in two shapes from the same sources: the household server in one container, as before, and a static site that runs in the browser alone.
The release workflow creates this release and appends the image digest line at the end of these notes by itself.

## What is in it

- The static site: the whole app without a server, live on GitHub Pages and attached to this release as a zip for any web root.
  It carries the five recorded voices, uses relative paths and hash routes, and so works in a subfolder without rewrite rules.
- In the static site the library lives in the browser's IndexedDB: workouts, collections, movements, the session log and the score corrections, with the same revision checks, pack imports and reimport detection as the server.
  The newest 2000 sessions are kept and older ones are dropped.
- Settings → General → This browser shows where the library lives, the storage used, whether the browser keeps it, and the counts.
  Keep data on this device asks the browser not to clear the library when space runs low.
- Download backup saves the whole library as `openwod-backup-YYYY-MM-DD.json`.
- The JSON export restores, in both shapes.
  Restore from backup reads the file, shows its counts and date, and after a confirmation replaces the whole library.
  The server first writes a copy of its database as `pre-restore-<timestamp>.sqlite` under `/data/backups/`, then replaces everything in one transaction.
  A backup from the static site restores into the server and the other way round.
- A pre-1.0 library left in a browser moves into the static site's library by itself on the first start, with one notice.
- The static site speaks of this browser where the server shape speaks of the server, and shows no server status in the header.
- Every `v*` tag now publishes the image, the static site on GitHub Pages and this GitHub Release with the zip, all gated on the smoke tests in Chromium, Firefox and WebKit.
  After the deployment the live site is tested once more in Chromium.
- The household's rules (revisions, imports, sessions, corrections, export and restore) live once in a shared package, so the server and the browser library behave the same.

## Supported browsers

Tested by the automated suite in WebKit, Firefox and Chromium engines, in both shapes.
Safari on macOS and iOS, Firefox and Chrome are the intended browsers.
Web Locks, BroadcastChannel and IndexedDB are required for recovery and single-tab control, and IndexedDB holds the library in the static site.
Browsers without them still play workouts, show "Not saving progress on this device", and never claim a recovery.

## Known limitations

- The static site keeps its library per browser and per browser profile.
  Two devices, or two browsers on one computer, each have a library of their own.
- The static site shares nothing across devices.
  A household that wants one library for everyone uses the container, and a backup file moves a library from one to the other.
- A browser may clear the static site's storage when the device runs low on space, unless it agreed to Keep data on this device.
  Download a backup now and then until it does.
- A private window loses the static site's library when it closes.
- No login.
  Keep the server on a trusted network or behind an authenticating proxy.
  The static site has no login either, but it also has no server to protect: everything stays in the browser that opened it.
- Over plain HTTP the screen wake lock, the single-tab lock and persistent storage are unavailable, because browsers offer them in a secure context alone.
  GitHub Pages is served over HTTPS.
- The installed web app has no offline copy of itself and needs the server or the site to start.
- Session events are uploaded once, with the finished session, not streamed while playing.
- The physical device checks are recorded per release by hand.
- The accent and rest colours, beep level and tone are device preferences, not shared through the household server.

## Upgrading

Set the stack's `APP_IMAGE` to the new tag or digest, re-pull and redeploy.
The schema is unchanged, so no migration runs and the previous image can be chosen again at any time.
The JSON export taken with Export all data under Settings → General now restores, into this server, a fresh stack or the static site.
Restore from backup replaces the household's library for every device, after the server has written its pre-restore copy.

The static site needs no upgrade: GitHub Pages serves the new release as soon as it is published, and its library stays in the browser.
