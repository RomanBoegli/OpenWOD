The household server now shares the settings across every device, and the screens before a workout fit a phone better.
The release workflow creates this release and appends the image digest line at the end of these notes by itself.

## What is in it

- On the household server the settings belong to the household.
  Theme, colours, background, sounds and voice, volumes, athlete names, kg or lb, your equipment, the difficulty scale and the training view options are stored once on the server, and every device follows them.
  A change reaches the other devices when they reload, come back to the tab or reconnect, and the last change wins.
  Each device keeps a copy, so the app starts at once and works offline, and a change made offline goes up once the server is back.
- On the first start after the upgrade the server has no settings yet.
  The first device that opens with settings of its own hands them to the server, and every other device takes them over, so open the device whose setup you want to keep first.
- The static site keeps its settings in the browser, as before.
- On a phone the library shows the workouts on the first screen.
  Sorting and the filter groups fold away behind a Filters button, which counts the filters that are on, and New workout, Import WOD and Export library share one compact row.
- On a phone the screen before the start is tighter and cleaner.
  The clock makes room for the percentage beside it, the station card, the buttons and the spacing are smaller, Details, All workouts and Export WOD share one row, and the Keys button is gone on touch screens.
- On a phone a workout's page puts Start workout, Duplicate (or Edit) and Export in one row, with Remove as an icon beside them.
- On a phone during a session the view switch is a small button inside the frame instead of overlapping its corner, the game plan in the context view is denser, and a recovered session shows a short note under Resume workout and End session instead of a second pair of the same buttons.
- On the household server the library says it is shared by every device, and a saved workout reads "Saved for the household" instead of "Saved on this device".
- The check of the live site after a Pages deployment is now a short one: it waits for the new site and confirms it serves this version.
  The browser tests have already run on the same files before the deployment.

## Supported browsers

Tested by the automated suite in WebKit, Firefox and Chromium engines, in both shapes.
Safari on macOS and iOS, Firefox and Chrome are the intended browsers.
Web Locks, BroadcastChannel and IndexedDB are required for recovery and single-tab control, and IndexedDB holds the library in the static site.
Browsers without them still play workouts, show "Not saving progress on this device", and never claim a recovery.

## Known limitations

- Settings follow the last change, with no merging.
  Two devices changing settings at the same time keep the later change.
- Another device picks up a settings change on reload, focus or reconnect, not while its screen stays open untouched.
- The JSON export carries no settings.
  The SQLite copies under `/data/backups/` and Download backup under Settings → General carry them.
- The static site keeps its library and its settings per browser and per browser profile.
- No login.
  Keep the server on a trusted network or behind an authenticating proxy.
- Over plain HTTP the screen wake lock, the single-tab lock and persistent storage are unavailable, because browsers offer them in a secure context alone.
- The installed web app has no offline copy of itself and needs the server or the site to start.
- Session events are uploaded once, with the finished session, not streamed while playing.

## Upgrading

Set the stack's `APP_IMAGE` to the new tag or digest, re-pull and redeploy.
On the first start the server writes `pre-migration-v1-to-v2-<timestamp>.sqlite` under `/data/backups/`, then adds the settings table in one transaction.
`/api/v1/health/ready` then reports `schemaVersion: 2`.

To roll back to 1.2.0, stop the stack and restore that pre-migration file as `/data/app.sqlite` before choosing the old image.
A 1.2.0 image refuses to start on a version 2 database and says so in its log, rather than misreading the data.

The static site needs no upgrade: GitHub Pages serves the new release as soon as it is published.
